How much does a local agent reveal to be rescued?

A small agent on company hardware works through a confidential data room. When it gets stuck it hands control to a cloud model for a couple of steps. Every byte the cloud receives is logged before it is sent and scanned for planted secrets, so we can compare which rescue packet keeps the rescue working while sending the least, and whether an outsider can force extra rescues.

The experiment suite · from the proposal (22–23 Nov 2026)

Three experiments on two task sets, about 3,640 runs in all

Every comparison is paired: the same tasks with the same seeds in every condition. 30% of tasks for tuning, 70% held out; at least 3 runs per task per condition; hypotheses and thresholds go on OSF before the final runs. Run counts below are the proposal's assumptions.

Pilot first (weeks 1–2). EnterpriseOps-Gym HR tasks and 10 TheAgentCompany tasks. Gate at the end of month 2: if the local model scores under ~10% partial credit on TheAgentCompany there is nothing to rescue, so EC2-Bench becomes the external benchmark. Only one external benchmark is kept.
Cloud-only baseline: 130 runs with prompt caching. Attacker passes: one per run, cheap model, Batch API. Budget (assumption): about US$1,600 at Fable 5.2 prices for the main study, plus about US$370 for E3 stage 2, near zero if the mentor-hosted model rescues.
  • H1Placeholders (P3) keep at least 80% of P0's rescue gain while cutting canary leakage by at least 75%. Primary.
  • H2Blanking (P2) loses significantly more rescue gain than P3, because the cloud can't tell redacted entities apart. Primary.
  • H3A privacy-aware trigger beats a privacy-blind one on score per unit leakage, at a matched number of rescues.
  • H4Leakage accumulates with rescues under P0 and P1; P3 flattens the curve (cumulative_curve in leakage.json).
  • H5Composite secrets are recovered by an attacker even when no single canary leaks. Exploratory.
  • H6Planted text makes the self-check say STUCK when it isn't; under P0 forced escalations add bystander leaks, under P3 close to none, and the actions-only view blocks the text attacks.

How it runs

One config per grid, one command, one folder of results

Offline checkpip install -e ".[dev]", pytest -q, then python -m codeblue run --config configs/mock.toml. Pure stdlib, Python 3.11+, no keys
1 · ServeOn the VM: scripts/azure/serve_9b.sh (local) and serve_cloud_27b.sh (stand-in cloud, already up on 8003); scripts/azure/tunnel.sh from a laptop. See docs/AZURE.md
2 · Pingcodeblue ping --config … and ping --cloud check endpoint, key and model name
3 · Runcodeblue run --config configs/azure-9b-local-27b-cloud.toml loops seeds × attacks × (packet, trigger) × tasks and writes runs/<timestamp>/
4 · Match the controlcodeblue matched-rate runs/<run>/episodes.jsonl → set random_rate, run the random arm
5 · Rescancodeblue scan <log> --room … works on any cloud log, including the proxy's (codeblue proxy --upstream …)
